# AIEF — AI Engineering Foundation

A provider-neutral engineering governance system for software built with AI coding agents.

It separates three kinds of knowledge that otherwise collapse into one unreusable file:

```text
FOUNDATION       how we work with agents        universal
    ↓ specializes
STACK PROFILE    how a rule is verified here    per ecosystem
    ↓ parameterizes
PROJECT PROFILE  what is true about this system per repository
```

Provider integrations are not a fourth layer. They are projections of the composed configuration, never independent policy sources.

## Status

|             |                                                                   |
| ----------- | ----------------------------------------------------------------- |
| Foundation  | **v0.3.1** — implementation baseline                              |
| Engine      | **working** — init, compose, health, render, baseline             |
| Conformance | **AIEF-Core.** `full` is refused by design while F5 is incomplete |

The engine governs this repository. `npm run verify` composes AIEF against its own Foundation, audits it, checks the projection for drift and runs the ratchet — so the claims on this page are the ones CI would fail on.

## Commands

```text
aief init       bootstrap a repository onto a referenced Foundation version
aief compose    resolve Foundation + Stack Profile(s) + Project Profile + Waivers
aief health     §48 configuration health and §55 layer-boundary tests, read-only
aief render     project the composition into a managed region of AGENTS.md
aief baseline   §46 quality ratchet, by violation identity
```

`baseline` is the only command that executes anything, and only commands a Stack Profile declared, only as argv, never through a shell. `compose`, `health`, `render` and `init` spawn no process, and a test enforces that (ADR-0006).

## Layout

```text
foundation/     normative specification (AIEF-000) and its rule sidecar
stacks/         ecosystem bindings — one profile per stack
providers/      adapter contracts; provider files are projections
plugins/aief/   the Claude Code plugin — skills and one command, no rules
schemas/        JSON Schema contracts, generated from the model
src/            the engine: model, load, resolve, audit, projection, ratchet, emit, cli
templates/      starting points to copy when adopting AIEF by hand
docs/adr/       architecture decision records
docs/specs/     work items: spec → plan → tasks
```

Directories appear when they have content. Nothing here is created speculatively — the specification says so, so the repository has to mean it.

## Conformance

Two levels, so that "this project follows AIEF" is a checkable claim rather than a declaration of intent:

- **AIEF-Core** — three layers, allocation test, intent/binding/parameters, verification evidence, change classification, visible waivers, clean layer separation, no load-bearing personal configuration, baseline-and-ratchet adoption.
- **AIEF-Full** — Core plus inspectable Effective Configuration, stable rule identity, orphan detection, failure on unwaived contradictions, health checks, layer-boundary tests, mechanical baseline monotonicity.

This engine refuses to compose a project that declares `full`, and names what is missing rather than pointing at a work item:

```text
F5  configuration health check — H4 stale rules, H8 unused roles and skills,
    H10 Stack Profile binding drift
```

F1–F4, F6 and F7 are delivered. Narrowing an honest refusal is worth more than removing it.

## Install into a project

As a dependency, for the CLI:

```bash
npm i -D github:Rogers-Ribeiro/aief
npx aief init --id <project> --stack node
npx aief compose
```

As a Claude Code plugin, for the procedures:

```text
/plugin marketplace add Rogers-Ribeiro/aief
/plugin install aief@aief
```

The plugin is a projection (§6). It ships the spec, plan, ADR and configuration-audit
procedures and one `/aief:status` command; it carries no engineering rules, because a rule that
existed only in a provider file would be a defect.
